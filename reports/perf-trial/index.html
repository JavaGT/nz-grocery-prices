Improvements

#1 · Memoized /api/deals (per-retailer TTL cache)

The deal computation (90-day observation query + calculateSales + calculateOngoingSales + sorting) is now computed once per retailer and reused for 5 minutes (DEALS_CACHE_TTL_MS env, 0 disables). Filter, limit, and signed-in tier ordering still apply per request; cached deal objects are never mutated (tier path copies).

Areaserver / deals pipeline (speed + CPU)
Before → Afterp50 107.4ms -> 0.26ms warm (~400x); cold cache-fill request unchanged ~150ms. 8-way burst was 8.5 req/s serialized - now bounded by JSON output only.
Trade-offsDeal feed can be up to 5 minutes staler than a full recompute (in practice prices only change on the nightly rebuild, so real staleness is unchanged). Memory measured with forced GC: server boots at ~63MB RSS; with all 6 retailer deal universes cached, live heap is only ~8MB total - RSS may climb to ~160MB transiently during a compute, but the uncached path had the identical spike on EVERY request. DEALS_CACHE_TTL_MS=0 restores exact old behavior.

#3 · Projection DB: 17MB -> 15.6MB and faster search

Three schema-level cuts to the rebuildable projection: (1) removed creation of the documented-dead deal_signals and product_matches tables; (2) removed the redundant idx_or_offer_key by reordering the offer_revisions UNIQUE constraint to (offer_key, observed_at, rev_hash) - same uniqueness, but the index now also serves offer lookups and ordering (EXPLAIN: no temp b-tree); (3) rebuild now sets PRAGMA page_size=8192 before WAL.

Areastorage / query speed (SQLite projection)
Before → AfterDB size 17MB -> 15.6MB (-8%). GET /api/products?search= p50 4.4ms -> 0.73ms (larger pages, shallower index). build-db time unchanged (~1.9s).
Trade-offsSchema edit relies on the projection being rebuildable (every rebuild builds a fresh temp DB - verified no code path re-applies migrations to an existing DB). Any external tool that reads deal_signals/product_matches or expects 4KB pages would break; none exist in this repo. 8KB pages cost slightly more RAM per cached page.

#4 · Web interface: wire weight -75%, zero-refetch view switches

Server side (by the web subagent lane, reviewed + merged by coordinator): static files served with brotli/gzip negotiation (variants compressed once per file version and cached in ~104KB of RAM), weak ETags with 304 revalidation (warm page reload transfers 0 bytes), memory-cached file reads keyed by mtime; JSON API responses gzip-compressed when over 1KB. Frontend: GET responses cached 30s with shared in-flight requests and full invalidation on any mutation, so switching views no longer refetches identical data; removed a DOM-allocating esc() helper that was also double-escaping ampersands (display bug fix - the DOM helper already escapes via text nodes).

Areainterface / network (speed + bandwidth)
Before → AfterCold SPA page load: 66,962 B -> 17,331 B brotli (-75%), 20,122 B gzip (-69%); warm reload = 0 B (13 x 304). GET /api/products?limit=120: 39,869 B -> 5,622 B (-86%). Loopback latency unchanged within noise.
Trade-offsgzipSync runs on the event loop (~0.2ms per 40KB API response) - fine vs the 107ms deals win it sits on top of; brotli's heavier compression is paid once per file version, not per request. Static assets keep max-age=3600 (no content hashes exist in a no-build repo, so HTML stays no-cache). API GET cache means up to 30s staleness, but every mutation clears it. Reviewed for security: the removed esc() was redundant (createTextNode escaping) and no innerHTML path takes unescaped product data.

Measured, deliberately not changed (honest stops)

  • Library JSONL load: 340ms / 216MB RSS on the 12MB archive (672ms / 540MB on the 22MB breadth archive). No consumer is on this path today (the app server uses SQLite and never holds the archive; collectors are network-bound; the old Workbench grocery project no longer exists). Speeding it up would mean weakening per-line hash verification - a data-integrity tradeoff for zero user-visible gain.
  • Fuzzy product matching: 0.17s on fresh DBs, capped at 1000 candidates - already fast.
  • local-archive-runner tests (~1.8s of the 2.8s suite): they exist to run the real shell script; faking the shell would weaken the guarantee.
  • Server memory: 63MB RSS at boot, ~8MB live heap even with all six retailer deal caches populated (measured with forced GC). No leak, nothing to reclaim.
