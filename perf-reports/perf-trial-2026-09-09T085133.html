Improvements — what changed and why

lib1. Archive load & query: cut clone churn + stream the loader (08fc98a)

CPU profiling showed ~105 ms of a 319 ms load inside structuredClone plus 32 ms of GC feeding it. Fixes: filter raw records before any cloning in ArchiveIndex.query() and materialize each surviving row exactly once; a loader fast path (applyParsed) skipping per-record deep clones for records fresh from JSON.parse; the repository streams decode+apply per line instead of buffering every line; eventTime memoized via WeakMap (records are immutable — existing invariant).

Trade-offs: applyParsed is only safe for exclusively-owned records (loudly documented; public apply()/applyAdditions() keep copy-on-apply, mutation-isolation test green). Streaming reader duplicates ~15 lines of chunk-split logic because repair/migrate CLIs still call the accumulating statics.

Deliberately rejected, with evidence: projection schema surgery — page-size sweep shows 8192 already optimal (16.76 vs 16.96–17.47 MB), every index costs 0.5–0.93 MB and is EXPLAIN-justified; string interning (~1–2 MB) and a validation-skip (~2–4 ms) rejected as complexity-dominant.

ui2. HTTP interface: in-memory suggestion index, one _meta read per request, precompressed static sidecars, browser-true benchmarks (06f0692, bfab763)

Suggestions was a full-table LIKE scan + DISTINCT + sort per keystroke; distinct product names (~8.8k strings, a few hundred KB) now cache in memory, invalidated by the same mtime probe the deals cache uses — wildcard queries keep the SQL path bit-for-bit (no FTS5). build:assets emits .br/.gz sidecars the dist server ships directly (dev public/ unchanged, lazy fallback kept). The bench now sends browser-like Accept-Encoding and reports wire/raw bytes + first-sample — it previously measured uncompressed wire only. Health p95 outlier investigated: client/undici first-sample artifact; server logs 0–1 ms, nothing to fix.

Trade-offs: brotli costs ~+0.27 ms p50 per JSON response for −83% bytes (right call off-loopback; <1 KB bodies deliberately stay identity). First suggestions request after boot/rebuild pays a one-time ~12 ms index build; startup pre-warm rejected to keep boot side-effect-free. SPA dynamic-import split rejected: ≤5 KB gain, breaks the modulepreload contract. zstd rejected: ~1–3% more for a third variant.

matching3. Cross-retailer matching: batched writes, cached statements, lazy fuzzy prep (bff4180)

Profile: 33% of runtime was per-pair prepare() recompiles + per-pair autocommit WAL commits (~1,500 writes), plus eager tokenize of all 42.7k products though the 1,000-candidate fuzzy cap stops far earlier. Fixes: one transaction around the persist batch (per-pair error accounting preserved — SQLite statement-level abort; feature-detect fallback for injectable doubles), the three hot pair statements cached, lazy per-group preparation so only brand groups the cap will actually reach get prepped, single-pass tokenizeName (identical output), unused column dropped from the CLI SELECT. Pair-table dumps byte-identical vs baseline at both scales (pair set, order, confidences, every evidence hash). Fuzzy stays candidate, never confirmed.

Trade-offs: batch commit means a mid-run crash loses the whole batch rather than partial pairs — acceptable for a re-runnable CLI (rerun/skip semantics unchanged and proven). Micro-opts in fuzz.js (~1.5 ms) rejected on profile evidence. Matching was already sub-second; this is an honest profile-justified half, not a hotspot hunt gone deep.

T1 · PERF3-T1 (issue #43) · Correctness question (pre-existing, unchanged by this trial): fuzzy pass updates previously auto-confirmed pairs.

During matching-lane profiling, 6 auto_gtin/auto_source_id-confirmed pairs were re-persisted by the fuzzy pass as updated rows. The hard rule says fuzzy candidates are never confirmed; whether a fuzzy candidate may overwrite a confirmed pair's row is undefined behavior today. The trial preserved existing behavior byte-for-byte rather than change semantics.

Decision question: should updateMatchPair refuse to move a confirmed pair back to candidate (Adopt), or is fuzzy-supersede intended and should just be documented (Reject / Adapt-as-doc)?

T2 · PERF3-T2 (issue #44) · Worth exploring: candidate + same-evidence-hash rerun skip.

Reruns could skip re-persisting candidate pairs whose evidence hash is unchanged. At the new 0.07 s runtime this buys almost nothing today; it would matter only if matching grows or is run in a hot loop.

Decision question (evaluation, not implementation): is rerun-skip worth the added state comparison, or close as premature?
