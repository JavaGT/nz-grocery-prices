Improvements — what changed and why

spa1. Single-scan filtered search; session/`_meta` statement reuse; client dialog leak fixed (769637c, 3b60124)

The products list ran the LIKE filter twice — once for the page, once for the total count. The page query now carries COUNT(*) OVER () (one scan serves both), with offset-past-end falling back to a standalone count (test-pinned). SQL 1.21–1.29 → 0.77–0.83 ms; HTTP p50 2.16/1.83 → 1.70/1.70 ms; response bytes identical across a 23-shape parity sweep. Per-request prepare() calls in the session lookup and the _meta freshness probe now reuse cached statements (9.7 → 2.7 µs per session lookup; −2.5 µs per JSON response). In the browser, the product detail dialog leaked one document keydown listener plus the dialog DOM on every button/overlay close — all close paths (Esc, button, overlay, backdrop) now funnel into dialog.close(), whose close event tears both down. Verified at code level + endpoint probes in Safari (visual pass pending, see below).

Trade-offs: windowed-COUNT semantics on offset-past-end pages preserved via the explicit fallback path (pinned by tests); statement memos assume one connection per server (true here) — none otherwise.

ingest2. Canonical fingerprint memo + direct serializer; streamed compaction; cheaper append-path clones (a5a814d, 9dff75a, 1f8c8ba)

Profiling showed fingerprint() re-deriving canonical key order for every record on every load/append. The locale-pinned key order is now memoized per object shape and canonical JSON is emitted by a direct serializer: archive load −4% (12.6 MB) / −13% (18.3 MB breadth); the nightly no-op append (where dedup hashing dominates) −26% / −33%. Compaction now streams records in ~1 MB chunks instead of building one giant string: −20% / −21% time, peak RSS 290 → 256 MB — same bytes, same single fsync, same atomic rename. The append path's structuredClone calls became a purpose-built cloneJson (append −17% / −29%), including a 6-line swap in archive-index.js the brief pre-approved.

Trade-offs: the serializer memo is bounded module state (key-order cache); the serializer reproduces the old comparator's integer-like-key quirk, now pinned by tests instead of by accident; cloneJson turns cyclic input into a stack-overflow instead of DataCloneError — both throw before anything persists, and non-plain-JSON values still take structuredClone. Durability untouched — no fsync weakened.

coordinator3. Docs drift corrected: the /api/deals → materialized-signals flip already landed (1b163b0)

This trial's planned "flip /api/deals to read materialized deal_signals" (the long-standing pending follow-up) turned out to be already implemented — defaultQueryDealSignals reads the table and the handler has no analytics imports (landed earlier in e58303b). AGENTS.md, the project map, the materializer comment, and DECISIONLOG all still described it as pending; they now describe reality, and the signal-parameter set is documented as pinned by the parity test. No behavior change — docs only.

analytics4. Analytics library: parse-once epoch sorts, fused filters, allocation-free price selection (7598410)

Profile showed the analytics passes spending their time in repeated ISO-date parsing, unfocused filter passes, and intermediate allocations. Fix: decorate-sort with epochs parsed once, fused filter passes, allocation-free selectEffectivePrice, and the ingest lane's cloneJson for output clones. calculateOngoingSales −65% / −43% / −38% at 12.6 / 37.6 / 87.6 MB; calculateSales and buildPriceSeries −14…−24%; full sweep 60 → 28 ms (12.6 MB) and 241 → 177 ms (87.6 MB). Outputs byte-identical across a 2,131-comparison parity harness (3 real archives + 300-case seeded fuzz + error-path parity); the rebuild's deal_signals parity test stays green.

Trade-offs: analytics now imports cloneJson, so cyclic input throws a different (still throwing) error. Honest framing: since deals are pre-materialized and the history endpoint reads SQLite, analytics now runs at rebuild time only — these wins are worth ~30–65 ms per nightly rebuild, not request latency. toAgentFeed (0.1–0.8 ms) and per-product series (0.03–0.08 ms) were profiled and left alone as already-optimal.

endurance5. Server proven steady at 1.16 M requests; two SPA memory leaks fixed; GET cache bounded (fe0c14d)

The memory lens found the server already at steady state: a 10-minute mixed workload (1,163,522 requests incl. authenticated paths, a scrypt register/login cycle, static files, deal rotation) shows flat post-GC RSS (−2.9 MB growth), boot peak 45.9 MB, and every long-lived structure audited as bounded (body cache ≤32 with TTL, deals cache single-slot with signature invalidation, suggestion index one slot). The heap profile's top allocators are one-time or irreducible per-request work — so no server change was landed; a keep-alive "fix" was even reverted when its test passed without it (the real hang was a bench-driver bug). The real wins were client-side: the price-history dialog never removed itself from the DOM (tens to hundreds of KB retained per "View price history" round-trip — now self-removing on close, with a guard for superseded dialogs); opening a detail dialog over an existing one bypassed the keydown teardown (now retires via close() so teardown runs); and the SPA GET cache kept one entry per URL forever (~29.5 MB retained at 500 viewed products — now TTL-pruned and evicted beyond 100 entries, eviction only removes so cache correctness is unchanged).

Trade-offs: cache eviction can refetch an old entry (a miss, never a wrong value); superseded-dialog guard adds one state check; multi-entry deals cache rejected — the SPA never sends retailer on /api/deals, so the rotation-thrash pattern it would fix doesn't occur (and it would raise worst-case memory).

JSON.parse of archive lines is ~4.5% of the load profile. A hand-rolled line parser could claw back part of that but re-implements JSON parsing on the authoritative-data path — the lane judged it high-risk/low-win and did not attempt it.

Decision question (evaluation): is trusted-archive fast-path parsing worth the risk, or close?

T6 · Worth exploring: in-memory products mirror for /api/products. GitHub #37

Would save ~0.6 ms per filtered list but introduces tie-order risk against the SQL-ordered results the API currently guarantees.

Decision question (evaluation): is 0.6 ms worth re-proving result ordering, or close?

T7 · Worth exploring (semantic tradeoff): session memoization. GitHub #38

Caching verified sessions would cut the (already memoized-statement) 2.7 µs lookup further, but introduces logout-staleness semantics — a logged-out session could serve from cache until invalidation. Security/perf tradeoff the lane declined to make unilaterally.

Decision question (evaluation): is the remaining µs worth logout-staleness reasoning, or close?

T8 · Worth exploring: rate-limit record DELETE-per-login. GitHub #39

Login currently deletes rate-limit rows per attempt; batching that write would reduce app.db write churn. Small; touches security-adjacent code.

Decision question (evaluation): worth the churn, or close?

T9 · Micro bundle: watch/prefs statement memos, single-pass router, search covering index. GitHub #40

T10 · Owner decision: cross-call epoch WeakMap in analytics. GitHub #41

Caching parsed epochs across analytics calls (module-level WeakMap keyed on observation objects) would save another ~15–25% on the materialization double pass. It requires extending analytics' purity contract — observations are currently treated as immutable-and-stateless inputs, and a cross-call cache couples call sites in a way the codebase has so far avoided (cf. the eventTime WeakMap the 08:51 trial added behind an explicit immutability invariant).

Decision question (evaluate before implementing): extend the purity contract for a one-off rebuild-time win, or close?

T11 · Build-it-or-delete-it: client dead code + a latent abort-signal risk. GitHub #42

Found by the endurance lane, left untouched: app.js currentCleanup is invoked by route() but no view ever sets it (dead mechanism, 4 lines); api.suggestions and api.health are exported client wrappers with zero callers; api.js anySignal attaches an abort listener to caller-supplied signals — no caller passes one today, so the accumulation risk is latent until a view passes a long-lived AbortSignal.

Decision question: delete the dead trio and note the anySignal contract (Adopt), keep them for planned views (Adapt — say which), or leave as is (Reject)?

Closed with evidence — no decision needed

Findings the lanes measured and rejected themselves: adapter parse micro-optimizations (0.4–3.6 µs/item ≈ 4 s CPU per campaign night vs a 60–70 min network-bound walk — collection is I/O-bound; note raw retailer payloads are not archived, so that bench used synthetic fixtures, caveated); JSON-round-trip cloning (drops undefined keys — not behavior-preserving); fingerprint WeakMap (no repeat-hash pattern at real scales); fsync batching (durability, declined on principle); projection schema surgery, string interning, zstd, SPA dynamic-import split (all closed by the 08:51 trial with page-size/byte evidence).

Method

Profile first (node --cpu-prof), repeatable bench scripts committed under perf-notes/, before/after medians on the same machine and real (copied, read-only) archive data at two scales (12.6 MB live archive + 18.3–27 MB breadth archives). Behavior-preserving: parity byte-dumps vs baseline wherever output shape matters; per-lane npm run check + full npm test green before any merge; the merge itself re-gated. Live retailer commands are never run; shared-checkout data/ is never written. Hard rules held: two-DB separation, no FTS5, fuzzy matches stay candidate-only, async scrypt only, collector.env secrets untouched.
